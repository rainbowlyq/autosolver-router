# LocalRepair

源码位置：`autosolver/strategies/local_search.py`

策略名：`local_repair`

## 实现逻辑

`LocalRepair` 是基于当前解的单点替换局部搜索。

入口逻辑：

1. 如果传入 `incumbent`，以它作为初始 `best`。
2. 如果 `incumbent is None`，先运行 `GreedyByScore()` 生成初始解。
3. 如果 `best is None`，返回空解。
4. 重复寻找一次单点替换，直到找不到改进或时间预算耗尽。

单点替换由 `_best_single_replacement()` 完成：

1. 将当前解的分配转为列表。
2. 枚举每一个待移除分配 `remove_index`。
3. 构造移除该分配后的 `kept`。
4. 统计 `kept` 中已使用骑手和已使用订单。
5. 遍历所有原始候选。
6. 如果候选骑手已被 `kept` 使用，则跳过。
7. 如果候选任务包内任一订单已被 `kept` 使用，则跳过。
8. 否则构造 `kept + [candidate]` 作为试探解。
9. 如果试探解比当前 `incumbent` 更好，则记录其中最好的一个。
10. 外层拿到替换解后，如果确实优于当前 `best`，就接受并继续下一轮。

是否更好由 `is_better_solution()` 判断：有效性优先，然后比较期望总分、分配数量和确定性签名。

## 不合理或欠佳点

- 只支持“一删一加”的替换，不支持只删除、不删除直接新增、一换多、多换一或多点重排。
- 如果某个已选候选本身有害，最优动作可能是直接删除；当前实现不会评估 `kept` 本身，因此无法做纯删除修复。
- 如果 `incumbent` 是空 `Solution` 而不是 `None`，策略不会回退到 `GreedyByScore`，会直接在空解上搜索并返回空解。
- 每次候选试探都会调用 `is_better_solution()`，内部会重新评估解，复杂度较高；在候选数量大时容易耗尽预算。
- 替换候选仍然被 `kept_tasks` 约束，不能给同一任务包追加骑手。
- 局部搜索容易陷入一阶局部最优。需要两个或多个同时变化才变好的 case 无法处理。
- 生成替换解时把新候选追加到列表末尾，虽然评估签名会排序，但输出顺序可能与原始构造策略不一致。

## 表现尚可的 case

- 贪心解整体不错，只存在少数局部错误选择。
- 一个候选替换另一个候选就能降低总分。
- 候选规模中等，能在时间预算内完成多轮扫描。
- 任务包冲突不太密集，替换后较容易找到合法候选。
- 当前最优解已有较高质量，局部搜索只承担微调职责。

## 表现会很差的 case

- 最优改进需要同时移除多个任务包再加入一个大包，或移除一个大包后加入多个小包。
- 当前解包含应直接删除的高成本候选，但没有更好的替代候选。
- 候选数量很大，完整枚举“一删一加”组合代价太高。
- 同一任务包多骑手强化是关键改进方向。
- 初始 incumbent 为空 `Solution`，且调用方没有传入 `None` 触发贪心回退。
