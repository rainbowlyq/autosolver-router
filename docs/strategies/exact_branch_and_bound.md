# ExactBranchAndBound

源码位置：`autosolver/strategies/exact.py`

策略名：`exact_branch_and_bound`

## 实现逻辑

`ExactBranchAndBound` 是一个限时递归搜索策略。它以骑手为分组单位，每个骑手最多选择一个候选，也可以不选择。

初始化参数：

- `max_seconds`：该策略最多使用的内部时间，默认 `0.5` 秒。
- `max_budget_fraction`：该策略最多使用剩余全局预算的比例，默认 `0.1`。

实际允许时间为：

```python
min(self.max_seconds, budget.remaining * self.max_budget_fraction)
```

主要流程：

1. 如果策略刚开始就已超时，返回 `incumbent` 或空解。
2. 调用 `_group_options_by_courier(instance)`：
   - 为每个候选创建 `_Option`。
   - 将任务 ID 转为任务下标。
   - 记录接单概率和单候选期望成本。
   - 按骑手分组。
   - 每个骑手组内优先大任务包，再按候选成本排序。
   - 骑手组整体也按最大任务包大小、候选数量和骑手 ID 排序。
3. 将 `incumbent` 转为当前 `best_solution` 和 `best_metrics`。
4. 从第一个骑手组开始递归搜索。
5. 对每个骑手组：
   - 尝试选择该骑手的每个候选。
   - 如果候选订单与已分配订单冲突，则跳过。
   - 更新每个任务的未覆盖概率、期望覆盖数、累计分配成本、已分配订单集合和分配列表。
   - 递归进入下一个骑手组。
   - 最后也搜索“不选择该骑手”的分支。
6. 每个递归状态都会用 `_state_metrics()` 计算当前部分解的总分，并和最优解比较。
7. 时间耗尽时停止搜索，返回已发现的最好解。

比较指标由 `_is_better_metrics()` 决定：

1. `total_score` 更低者更好。
2. 总分相同，`assignment_count` 更少者更好。
3. 仍相同，`signature` 字典序更小者更好。

## 不合理或欠佳点

- 名称包含 `BranchAndBound`，但当前实现没有真正的 bound 剪枝。它是带时间限制的深度优先枚举，主要剪枝只有时间检查和订单冲突检查。
- 搜索空间随骑手数量和每个骑手候选数量指数增长，大实例中通常无法穷尽。
- 默认只使用最多 `0.5` 秒且不超过剩余预算的 `10%`，在大多数大规模 case 上只能搜索很小一部分空间。
- 虽然递归状态维护了 `covered_tasks` 和任务未覆盖概率，但最终 `_is_better_metrics()` 不比较 `covered_tasks`，只比较 `total_score`、分配数和签名。
- `assigned_task_indexes` 禁止订单重复，因此同一任务包不能被多个骑手同时选择；这与评估器支持“同包多骑手联合接单”的能力不一致。
- `_state_metrics()` 使用“已分配订单数”计算未分配罚分，部分解在递归中也会被当作可行解比较。这符合当前目标函数，但会偏向跳过高成本任务，而不是追求覆盖率。
- 没有利用 incumbent 生成搜索上界，也没有根据剩余骑手可达任务计算乐观下界来提前剪枝。

## 表现尚可的 case

- 骑手数量少，每个骑手候选数量少，搜索能在时间内接近穷尽。
- 存在明显应该“不分配”的高成本候选，贪心会误选，而递归搜索能探索跳过分支。
- 候选冲突结构简单，早期分组排序容易碰到较优组合。
- `incumbent` 已经较好，策略只需要在小范围内找到额外改进。
- 单任务包单骑手模型足够表达最优解，不依赖同包多骑手强化。

## 表现会很差的 case

- 大规模数据，例如几十个任务、几十个骑手、数万候选。
- 每个骑手有大量候选，分支因子很高。
- 最优解需要同一任务包分配多个骑手。
- 需要覆盖率优先，而不是当前代码中的总分优先。
- 好解位于搜索顺序较靠后的分支，时间预算耗尽前无法访问。
- 需要真正的分支定界剪枝才能处理的密集冲突图。
